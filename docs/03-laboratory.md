# UI автоматизация Testboard

**Статус: для предварительного ознакомления — после блока практик.** Можно изучить условие, варианты и критерии оценки заранее. Выполнять и сдавать лабораторную сейчас не требуется. Начинайте после первой практики, [практики по архитектуре](02-architecture.md) и объявления преподавателя; вариант уточните у преподавателя.

**Тип:** Лабораторная работа

**Ключевая точка:** Нет

**Ссылка на условие:** [Требования к проверкам](#требования-к-проверкам)

**Максимальный балл:** 15

## Что можно подготовить заранее

- Прочитать сценарии C1–C5, F1–F5, варианты и критерии оценки, записать вопросы.
- Посмотреть на Testboard каталог и избранное, прочитать сценарии создания объявлений; изучить спецификацию API по ссылке ниже.
- Разобраться, какие данные потребуются тестам и что нужно удалять после каждого теста.

Для текущей практики не требуется создавать учебного продавца, настраивать .env или писать API-подготовку. Эти действия понадобятся при выполнении лабораторной.

## Цель

Научиться самостоятельно собирать проект на JavaScript и Playwright, применять Page Object и проверять создание объявлений и избранное через интерфейс Testboard.

Результат работы — ваш учебный форк с минимум двенадцатью независимыми UI-тестами лабораторной: пять для создания объявлений, пять общих для избранного и два по назначенному варианту. Подготовку данных и очистку после тестов вы реализуете самостоятельно. Максимальная оценка — **15 баллов**.

## Вводные для выполнения лабораторной работы

- [Учебный сайт Testboard](https://testboard.avito.com/).
- [Спецификация API Testboard](https://testboard.avito.com/docs/swagger.json). API используется для авторизации и подготовки данных; проверяемые пользовательские действия выполняются через UI.
- Ваш форк [web-tests-student](https://github.com/qa-course-avito/web-tests-student) с выполненной практикой по архитектуре. Лабораторную добавляйте в тот же проект.
- Стек работы — JavaScript и Playwright Test. Нужен Node.js версии, указанной в package.json заготовки.

Для создания объявлений нужен учебный продавец. Зарегистрируйте его вручную один раз и сохраните E2E_USER_EMAIL и E2E_USER_PASSWORD в локальном .env. Один аккаунт можно использовать между прогонами; регистрировать пользователя перед каждым тестом не требуется.

Сценарии избранного выполняйте гостем в новом контексте браузера. Testboard сохраняет гостевое избранное в этом браузере. Объявления для предусловий создавайте через API от имени продавца, а его авторизацию применяйте только к UI-тестам создания. Авторизованный продавец не может добавить собственное объявление в избранное. Второй аккаунт для обязательной части не нужен.

## Как выполнять лабораторную работу

1. Продолжите работу в своём форке web-tests-student после практики по архитектуре. Уточните у преподавателя вариант. Проверьте установку зависимостей командой npm ci и браузера командой npx playwright install chromium.
2. Изучите форму создания, каталог, страницу объявления и избранное. Найдите устойчивые локаторы в DevTools и определите ожидаемый результат каждого теста.
3. Заполните локальный .env по .env.example. Реализуйте вход через API, генерацию уникальных данных, создание объявлений с фото для предусловий, сохранение их ID и безопасную очистку.
4. Развивайте pages, tests, helpers и configs из практики по архитектуре; добавьте fixtures для подготовки и завершения тестов. Для загрузки можно использовать подготовленную фотографию assets/test-photo.png или добавить свою. Повторяющуюся карточку можно выделить в components.
5. Напишите пять тестов создания и пять общих тестов избранного. Затем выполните два теста своего варианта. Негативные сценарии обязательны для каждого варианта; проверяйте конкретную ошибку или пустой результат и сохранность состояния.
6. Проверьте каждый тест отдельно и весь набор три раза подряд. Убедитесь, что очистка выполняется и при падении проверки. Для разбора ошибок используйте отчёт и trace.
7. Заполните README: вариант, покрытие, установка, настройка данных без секретов, команды запуска и получение отчёта. Удалите выполненные TODO.
8. Отправьте преподавателю ссылку на тот же форк, ветку main и SHA проверяемого коммита. Репозиторий должен быть доступен преподавателю. Учётные данные и сохранённые сессии в него не добавляйте.

Если поведение сайта расходится с условием, зафиксируйте шаги, ожидаемый и фактический результат в README и обсудите расхождение с преподавателем. Не заменяйте падающую проверку пустым тестом или безусловным пропуском.

## Требования к проверкам

**Количество проверок**

Обязательный минимум — **12 тестов**: C1–C5, F1–F5 и два теста одного назначенного варианта. Все три варианта выполнять не требуется. Дополнительные тесты не увеличивают максимальную оценку.

Сохраните три теста практики по архитектуре в tests/practice. Лабораторные тесты добавьте в tests/create и tests/favorites. После выполнения работы в проекте будет минимум 15 тестов: три теста практики и двенадцать лабораторных.

**Позитивные и негативные сценарии**

Для любого варианта обязательны пять негативных сценариев: C2, C3, C4, C5 и F5. В них приложение должно отклонить недопустимое действие или показать пустой результат поиска. Сам автотест проходит, когда это ожидаемое поведение подтверждено. В C4 и C5 все остальные поля и фотография должны быть корректными, чтобы проверить одно ограничение за раз.

**Блок 1 Создание объявления через UI**

- **C1 Успешное создание.** Авторизуйте продавца, откройте форму, заполните название, описание, цену и количество, загрузите фотографию и отправьте форму. На странице созданного объявления проверьте значения всех полей и видимость фото. Сохраните ID для очистки. Создание через API не заменяет этот тест.
- **C2 Обязательные поля.** Откройте форму продавцом и отправьте без обязательных значений. Проверьте сообщения «Введите название объявления», «Добавьте описание», «Загрузите хотя бы одну фотографию» и сохранение формы на экране. Успешного создания быть не должно. Форма использует собственную валидацию с noValidate.
- **C3 Гостевой доступ.** В новом гостевом контексте откройте /advertisements/create. Проверьте переход на /auth/login и видимый заголовок «Вход в аккаунт».
- **C4 Цена выше максимума.** Заполните корректные название, описание и фотографию, задайте количество 2 и цену 1 000 001 ₽ при максимуме 1 000 000 ₽. Отправьте форму. Проверьте сообщение «Цена не должна превышать 1 000 000 ₽», сохранение формы и введённых значений. Запрос создания не должен отправляться, перехода к списку объявлений быть не должно.
- **C5 Количество выше максимума.** Заполните остальные поля корректно, например с ценой 1234 ₽, включите «Несколько штук в наличии» и введите 101 при максимуме 100. Отправьте форму. Проверьте сообщение «Количество не должно превышать 100», сохранение формы и значений. Запрос создания не должен отправляться, перехода к списку объявлений быть не должно.

**Блок 2 Избранное**

Выполните пять общих тестов. Каждый тест самостоятельно создаёт своё начальное состояние.

- **F1 Пустое избранное.** В новом контексте откройте /favorites. Проверьте заголовок «Избранное», сообщение «В избранном пока пусто» и отсутствие карточек.
- **F2 Добавление из каталога.** Найдите собственное подготовленное объявление и нажмите сердечко. Проверьте выбранное состояние, затем наличие в избранном карточки с нужными UUID и названием.
- **F3 Сохранение после обновления.** Добавьте объявление, откройте избранное и обновите страницу. Проверьте, что нужная карточка осталась, а сердечко выбрано. Не используйте результат F2.
- **F4 Удаление из избранного.** Добавьте одно объявление и удалите его на странице избранного. Проверьте отсутствие его карточки и пустое состояние. Вернитесь к этому объявлению и проверьте невыбранное сердечко.
- **F5 Поиск без совпадений.** Самостоятельно подготовьте и добавьте два объявления. Введите уникальный запрос, отсутствующий в обоих названиях. Проверьте отсутствие карточек и сообщение «В избранном пока пусто»: текущий UI использует его и для пустой выдачи поиска. Очистите запрос и проверьте возвращение обеих карточек по UUID и названиям, а также выбранные сердечки. Поиск не должен удалять избранное.

Выбранное состояние проверяйте по aria-pressed="true" или data-favorited="true" у [data-marker="favorite-button"]. Это HTML-элемент button; в коде используйте его фактическую роль и атрибуты.

**Вариант 1 Каталог и независимость карточек**

- **V1.1 Повторное нажатие.** Добавьте объявление из каталога и повторно нажмите то же сердечко. Проверьте невыбранное состояние и отсутствие этого объявления в избранном.
- **V1.2 Два объявления.** Добавьте два подготовленных объявления и удалите одно. Проверьте отсутствие удалённого UUID и сохранение второго. Проверки общего количества карточек недостаточно.

**Вариант 2 Страница объявления**

- **V2.1 Добавление из объявления.** Откройте /advertisements/<UUID>, проверьте нужный заголовок и добавьте объявление в избранное. Проверьте выбранное сердечко и наличие этой карточки на странице избранного.
- **V2.2 Согласованность состояния.** Добавьте объявление на его странице, удалите в избранном и снова откройте страницу объявления. Проверьте невыбранное сердечко. Все действия выполняются в одном контексте, без зависимости от другого теста.

**Вариант 3 Поиск и сортировка избранного**

- **V3.1 Поиск по существующему названию.** Добавьте два объявления. Найдите первое по уникальному названию, проверьте его UUID и отсутствие второго. Очистите поиск и проверьте возвращение обоих объявлений. Негативный поиск без совпадений уже проверяется в общем тесте F5.
- **V3.2 Сортировка по цене.** Добавьте два объявления с разными известными ценами. Выберите сначала дешёвые, затем дорогие. В обоих направлениях проверьте порядок двух UUID, а не порядок добавления в избранное.

**Подготовка данных и независимость**

- Реализуйте самостоятельно API-авторизацию продавца, генератор уникальных названий, создание объявлений с фото и cleanup. Готовые UUID от преподавателя не используются. Проверки API-кодов 401 и несуществующего ad_id не входят в эту UI-работу.
- Каждый тест получает собственные данные. Находите нужное объявление по точному уникальному названию и UUID из ответа создания. Не выбирайте случайную первую карточку и не опирайтесь на общее число объявлений сайта.
- Для сценария с двумя объявлениями подготовьте два собственных объекта. Для сортировки задайте им разные известные цены.
- Сохраняйте ID сразу после создания. Очистка должна выполняться после каждого теста, включая падение проверки, например в finally или teardown фикстуры. Удаляйте только зарегистрированные ID текущего теста с проверкой владельца. Очистка всех объявлений аккаунта запрещена.
- Каждый test() получает новый browser context. Для избранного он гостевой, для авторизованных сценариев создания — с сессией продавца. Тесты не используют данные или состояние предыдущего теста.
- Проверяйте наблюдаемый UI-результат с помощью expect. Все асинхронные действия выполняйте с await. Фиксированная задержка не заменяет ожидание состояния элемента.

<summary>Подсказки, если застряли</summary>

**Кто создаёт объявление, а кто нажимает сердечко?** Для теста избранного подготовьте объявление с фото через API от имени продавца. Каталог откройте гостем в новом контексте браузера. Найдите карточку своего объявления, нажмите сердечко и проверьте результат через UI. В сценарии C1 создание само входит в проверку, поэтому продавец заполняет и отправляет форму через UI.

**Когда сохранять ID объявления?** Сразу после успешного создания, до первой проверки результата. Это относится и к C1: ID можно получить из ответа на запрос, который отправляет форма. Если проверка фотографии упадёт, у теста уже будет ID для очистки.

**Что произойдёт с данными, если упадёт `expect`?** В тестовой фикстуре Playwright код до `await use(...)` готовит данные, а после него выполняется очистка. Храните ID отдельно для каждого теста. При очистке проверьте владельца и удалите только объявления этого теста. Чтобы проверить себя, намеренно уроните проверку после создания объявления и убедитесь, что оно удалилось, а остальные объявления продавца остались на месте.

## Требования к оформлению

**Результат сдаётся в том же форке GitHub, где выполнены обе практики.**

- pages содержит страницы создания, каталога, объявления и избранного. В Page Object размещайте локаторы и действия со страницей; основные проверки результата оставляйте в tests. components используйте при необходимости.
- tests содержит отдельные сценарии создания и избранного с понятными названиями, входными значениями и ожидаемыми результатами.
- helpers содержит технические функции и работу с API. configs — адрес сайта и проверку наличия учётных данных. fixtures — подготовку и завершение теста, assets — фотографию. Не создавайте абстракции без задачи.
- В репозитории есть package.json, package-lock.json, playwright.config.js, .env.example, .gitignore и README. Учётные данные вводятся только в локальный .env.
- В README укажите назначенный вариант, соответствие тестов C1–C5, F1–F5 и своему варианту, отметьте позитивные и негативные сценарии, опишите настройку данных, команды запуска, получение отчёта и trace. Описание должно позволять другому человеку запустить проект.
- В Git не попадают .env, пароли, токены, node_modules, отчёты, trace и браузерные профили. Удалите неиспользуемый код и незавершённые TODO обязательных сценариев.

**Проверка перед сдачей**

Выполните команды из корня своего проекта после настройки .env. Общий запуск включает практику и лабораторную. Помимо общего запуска проверьте, что каждый тест запускается отдельно. Только лабораторные тесты можно запустить командой npm test -- tests/create tests/favorites.

```bash
npm ci
npx playwright install chromium
npm test
npm test -- --repeat-each=3
npx playwright show-report
```

## Критерии оценки

Максимальная оценка — **15 баллов**. Баллы по десяти критериям суммируются. Оцениваются работающие проверки и подтверждающие их результат assertions.

**1 Успешное создание через UI — до 2 баллов**

- **2 балла:** объявление создаётся через форму; проверены название, описание, цена, количество и видимость фото.
- **1 балл:** создание через UI работает, но проверки результата неполны.
- **0 баллов:** тест отсутствует, не создаёт объявление через UI или заменяет создание вызовом API.

**2 Негативная валидация формы — до 3 баллов**

По одному баллу за полностью выполненные C2, C4 и C5. Для C2 проверены три ошибки обязательных полей и сохранение формы. Для C4 и C5 проверены конкретная ошибка, сохранность введённых данных и блокировка отправки создания. Остальные значения в каждом из этих двух тестов корректны.

- **3 балла:** выполнены все три сценария.
- **2 балла:** выполнены два сценария.
- **1 балл:** выполнен один сценарий.
- **0 баллов:** ни один сценарий не выполнен полностью.

**3 Гостевой доступ к созданию — до 1 балла**

- **1 балл:** в новом гостевом контексте проверены переход на /auth/login и заголовок «Вход в аккаунт».
- **0 баллов:** сценарий отсутствует или не проверяет оба условия.

**4 Самостоятельная подготовка данных и очистка — до 2 баллов**

- **2 балла:** реализованы API-авторизация, уникальные данные и создание с фото; cleanup работает при падении и удаляет только сохранённые ID текущего теста с проверкой владельца.
- **1 балл:** собственная подготовка и безопасная очистка реализованы, но очистка при падении не обеспечена.
- **0 баллов:** подготовка отсутствует, используются чужие или готовые UUID, либо очистка может удалить посторонние объявления.

**5 Основные сценарии избранного и негативный поиск — до 2 баллов**

- **2 балла:** выполнены F1, F2, F4 и F5; проверены нужные UUID, состояния сердечка, пустое состояние и возвращение избранного после очистки поиска.
- **1 балл:** работает только часть этих сценариев или часть проверок результата отсутствует.
- **0 баллов:** сценарии отсутствуют или не проверяют результат работы избранного.

**6 Сохранение избранного после обновления — до 1 балла**

- **1 балл:** F3 самостоятельно готовит состояние и проверяет карточку и сердечко после обновления.
- **0 баллов:** сценарий отсутствует, неполон или зависит от другого теста.

**7 Два теста назначенного варианта — до 1 балла**

- **1 балл:** оба теста варианта выполняются и проверяют все указанные для них результаты.
- **0 баллов:** хотя бы один из двух тестов не выполнен полностью.

**8 Разделение ответственности модулей — до 1 балла**
